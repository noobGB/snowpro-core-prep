Product & design specification v0.1 · 2026-08-16

SnowPro Core Prep

A local, offline-first study app for the Snowflake SnowPro Core certification (COF-C03), built on an existing folder of verified domain notes, practice questions and mock exams.

This document is written to be built from without the author in the loop. It is stack-agnostic: it specifies behaviour, content structure and visual tokens, not a framework.

Open decision

The brief supplied a dark "midnight precision" style reference, and a light editorial design system (Classical) was also attached to the project. This spec follows the dark reference. If the Classical system is the real intent, the token table in §3 is the only section that has to change — every layout below survives the swap.

1  Overview

The study material already exists as markdown: five domain files verified against the official COF-C03 guide, fifty domain-tagged practice questions, a hundred-question mock, a cheatsheet of hard numbers, a day-by-day plan, a resource list and a hands-on setup log. The app's job is to turn reading material into measured practice — to answer "am I ready, and where am I weakest" with numbers rather than a feeling.

It runs locally with no account and no backend. Progress lives in browser storage. Content is generated from the markdown by a script, so the notes stay the human-editable source of truth and new mock exams can be dropped into the folder later.

Principles

  • Exam-faithful. Scaled 0–1000 scoring against the 750 line, strict mock timing, answers withheld until submit.
  • Content grows, app adapts. Nothing about the app assumes one mock or fifty questions.
  • Measurement over decoration. Every number on screen changes what you study next.
  • Quiet surface. Near-black canvas, hairline borders, one accent, no ornament.

The accent choice was left open in the brief. Teal is proposed over the reference's acid lime: lime is strongly associated with the referenced product, teal reads cold and sits closer to the subject matter. Status colours are separate and used only for correctness: #27a644 correct, #eb5757 incorrect, #c9bb4a partial or warning. They never appear as decoration or as chart fills.

Notes prose is not inlined into content.json. The script emits one notes/<domainId>.json per domain holding the parsed heading tree and HTML, so the reader loads only what it displays and the search index can be built once at generation time into search-index.json.

Progress

Progress is one serialisable object with a single writer. In the container it is a file on the mounted data volume (/data/progress.json), read on boot and written back on every change through a two-route storage adapter (GET /api/progress, PUT /api/progress). Opened without the container it falls back to localStorage under the same key and the same shape, so nothing above this line changes with the storage target. Writes are debounced to roughly one per second and always write the whole object — no partial merges, no migrations at write time.

/data/progress.json  (container)  ·  localStorage["snowprep.progress"]  (fallback)

  "examDate": "2026-08-19",
  "lastLocation": { "route": "/notes/d3", "label": "Domain 3 — Data Loading", "at": "…" },
  "attempts": [

      "bankVersion": "2026-08-16T09:12:00Z",

Every attempt stamps the bankVersion it ran against. Attempts are never deleted or migrated when content changes; those taken against an older bank are labelled in analytics and excluded from same-set trend comparisons unless the user opts in.

Derived numbers

Number Rule
Question creditSingle-answer: 1 or 0. Multi-select partial credit: (correct picked − incorrect picked) ÷ correct total, floored at 0.
Scaled scoreround(credit ÷ answerable × 1000). Pass line drawn at 750. Unanswered questions count as zero in a submitted attempt.
Domain readinessScaled score across that domain's questions in the three most recent attempts touching it. Practice and mock count equally. Blank until at least one attempt exists.
Overall readinessDomain readiness weighted 31/21/20/18/10. Domains with no data are excluded and the weights renormalised, with a note saying how much of the exam is unmeasured.
Days leftWhole days from today to examDate, local time. Zero reads "today"; past reads "exam passed" and offers to set a new date.

5  Content pipeline

A single script reads the study folder and writes the JSON the app loads. It runs at container start against the mounted content volume, and can be run by hand after editing any markdown; the app never parses markdown at runtime.

Discovery by filename

0[1-5]_Domain<n>_*.md          → domain notes
1[0-4]_Practice_Questions_*.md → domain question sets
1[6-9]|[2-9][0-9]_Mock_Exam_<n>.md → a mock exam (any number, discovered automatically)
08_Cheatsheet_*.md             → flashcards
00_Study_Plan.md               → plan
07_Resources.md                → resources
15_Hands_On_*.md               → setup walkthrough

Dropping 17_Mock_Exam_2.md into the folder and rerunning the script is the whole workflow for adding a mock. Domain assignment for mock questions comes from the file's own domain headings; where a mock reuses a question already present in a domain file, the script matches on the normalised stem and reuses the question id rather than duplicating it.

Expected markdown shape

Questions are numbered **n.** followed by the stem, then options as lines beginning A. through E.; an answer-key section at the foot maps number to letters and explanation. Multi-select is detected from a key holding more than one letter, or a stem containing "select two" / "choose two".

Failure behaviour

The script fails loudly and writes nothing if it hits a question it cannot parse. The error names the file, the question number, the line, and what it expected — for example: 16_Mock_Exam_1.md Q63 (line 812): answer key lists "F" but only options A–D were found. A partial import is never produced, so the app can trust that content.json is complete.

  • Sticky bar is the only navigation aid: answered count, a thin fill, the timer when timed, and submit. No question navigator rail, no jump list.
  • Multi-select questions state how many to choose and use square targets; single-answer use round ones. Selection is togglable up to submit.
  • Submit asks for confirmation when anything is unanswered, naming the count. Unanswered questions score zero.
  • Leaving mid-session (practice): the attempt is scored on what was answered and logged with status partial. Partial attempts are visibly marked everywhere they appear and are excluded from readiness unless they cover at least half the set.
  • Mock timing is strict: the timer runs from start, cannot be paused, warns at ten minutes with an inline banner (no modal), and auto-submits at zero with status expired. Closing the tab does not stop the clock — elapsed time is computed from the start timestamp on return.
  • Answer state is written to storage on every change so a crash costs nothing.
  • Per-question time is recorded from when the question first enters the viewport to when it last receives an answer, feeding the timing view in analytics.

8  Risks and open questions

Risk Response
Markdown driftFuture files may not match today's question formatting. The parser fails loudly with file, question and line, so a mismatch is a five-minute fix rather than a silent gap in a mock.
Duplicate questions across filesMock 1 reuses the fifty domain questions. Stem-normalised matching reuses ids so the wrong-answer notebook and readiness don't double-count; near-identical but edited stems will occasionally slip through and create a duplicate.
Thin sample sizeDomain 5 has five questions; one miss swings its readiness 200 points. Domains under ten questions show their score with a "low sample" note rather than pretending precision.
Memorisation, not learningA fifty-question bank is quickly memorised, inflating readiness. Shuffled answer order is deliberately not in v1 to keep review stable; if scores plateau near 1000 the honest fix is more questions, and the analytics copy should say so.
Progress lossThe data volume removes the browser-storage risk, but only while the container is the way in: opening the files directly falls back to localStorage and those attempts never reach the volume. The header shows which store is active so the two can't be silently mixed.
Volume permissionsA container user that cannot write /data turns every save into a silent no-op. The server writes a probe file at boot and refuses to start if it fails.
Content licensingThe questions are original and the guide PDF is Snowflake's. If the repo goes public, the PDF should not be committed and the app should link to Snowflake's download instead.
Exam versionCOF-C03 is current; Snowflake revises the guide periodically. Content carries the exam version so a future revision can coexist rather than overwrite.

Decided by default

Three questions went unanswered in planning and were resolved here: the accent colour (teal, §3), what Resume returns to (last location, unless an attempt is incomplete), and how readiness is displayed (one overall figure above five domain bars). Each is a one-line change if the call was wrong.

9  Shipping the open-source version

The deployment target is Docker with mounted volumes, so both the study material and the accumulated progress outlive the container. That decision is what makes the storage adapter in §4 worth having: it is the only place the app knows where its data lives.

/content   ← the markdown study folder, mounted read-write from the host
/app/dist  ← generated JSON + built frontend, produced from /content
/data      ← progress.json, mounted read-write; the only file the app writes

On container start the pipeline runs against /content before the server binds. Adding 17_Mock_Exam_2.md to the host folder and restarting the container is the whole workflow; no image rebuild. If the pipeline fails, the container exits with the parse error rather than serving stale or partial content — the loud-failure rule from §5 applies at boot.

The server is minimal: static files plus the two progress routes. No database, no auth, no sessions. A single-user local tool does not need them, and adding them later is a decision about multi-device sync, not about persistence — persistence is already solved by the volume.

Now — volume-backed single user

One compose file, two volumes, one command to run.

Progress survives restarts, rebuilds and browser resets, and can be backed up by copying a single file. Still one machine: nothing syncs between devices.

Later — accounts and sync

The same two routes, keyed by user, backed by a database instead of a file.

Buys multi-device and shared question banks at the cost of auth, migrations, privacy obligations and hosting — a different project, and only worth it if the tool finds real users.

Two details keep the second column cheap: the progress object is a single blob a sync endpoint can accept wholesale, and schemaVersion is already stamped so a server can migrate old payloads on read.

For a public repo: keep the markdown as the contribution surface (a new mock is a pull request adding one file), keep the guide PDF out of the repo, and make the pipeline's failure messages good — they will be the main thing contributors interact with.
